# Docker 应用升级

先根据请求确定是隔离演练还是切换现有服务。目标容器、Compose 服务、目标版本或执行方式有多种可能时，先只读盘点，再合并询问关键缺项。

1. 用 docker context show、docker ps -a 和 docker inspect 核实目标、运行状态、原镜像 ID、挂载、端口、网络、重启策略及自定义配置。Compose 以实际项目和覆盖文件为准。保护配置中的凭据。
2. 根据应用官方升级说明核实版本跨度、数据库迁移条件、必要中间版本和支持的备份方式。识别卷、绑定目录、外部数据库及可写层中的业务数据。信息不足时暂停切换。
3. 停机前拉取目标镜像，记录实际摘要。latest 是可变标签，比较镜像 ID 决定是否需要重建。隔离演练使用独立卷、容器名和本机临时端口，隔离外部连接。演练完成后记录结果。用户要求切换现有服务时继续下一步。
4. 停止服务或写入前，核对用户是否已授权此次目标版本、服务范围、停机安排和已知迁移影响。缺少授权时，一次说明具体目标、预计影响和回退条件，等待确认。用户已明确同意的事项直接沿用。
5. 记录业务基线，停止写入，备份数据和配置并验证备份可读。数据库按应用支持的方式导出或一致性快照。备份失败则恢复原服务。无状态应用可在确认无持久数据后跳过数据备份。
6. 通过原部署方式替换镜像，保留必要参数并显式复用命名卷、匿名卷或绑定目录。只允许一个写入实例。按项目和服务限定 Compose 操作。保留旧镜像并防止旧容器自动启动。
7. 核对实际镜像 ID、应用版本、健康状态、迁移日志、访问端点和代表性数据。区分挂载探针、应用可用性和登录后的业务测试。记录已验证范围、备份位置和回退条件。
8. 新版尚未写入时可恢复旧配置和镜像。发生迁移后，先停止新版，用独立卷及匹配的外部存储恢复升级前状态，再验证旧版。保留升级后写入，确认数据处理方式后切换。

升级 MaxKB 时，结合 [MaxKB 升级示例](examples/maxkb.md)核实版本路径、持久化目录和业务验收条件。
