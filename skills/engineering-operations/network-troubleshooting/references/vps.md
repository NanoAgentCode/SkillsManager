# VPS 排查

## 确认当前配置与两段连接

1. **核对运行时。** 从当前活动的 FlClash 配置和连接记录确认代理模式、规则、完整选组链、节点实际服务器、端口和地址族。脚本或覆写可能注入同名节点。节点未加载或引用缺失时，先校验并重新应用正确的配置。已有单文件配置可用独立的节点名和一个 `select` 组统一切换，按用户需要保留 `DIRECT` 选项和原分流。节点入口意外被送回自己的代理时，核对入口的实际选路并修复循环。
2. **验证客户端到 VPS。** 用 [直连排查](direct.md) 按地址族测实际的 SSH 端口或代理端口。备用节点和独立网络可以用于同一时段对照。TCP 通了以后再看 SSH banner、主机指纹和认证，或继续验证 Shadowsocks 协议与转发。若 TCP 未握手，先查入口和回程。通过服务商控制台/VNC 核对主机指纹与实际监听，保留已有管理会话。
3. **验证 VPS 到目标。** 先从 VPS 本机请求同一个目标，必要时用与服务端匹配的本地代理客户端验证协议、加密方式和转发，再在 FlClash 上发起同样的请求。节点测速结果取决于检测地址，耗时可含解析、建连和目标响应。业务验收使用原目标并查看实时连接链；出口 IP 用用户认可的地址回显服务验证，同时确认回显请求也命中同一节点。IPv6 入口与 IPv4 出站可以同时成立，各自记录。

可用应用本身发请求，或将 curl 显式指向当前配置中的本地 HTTP/mixed 端口。确认 `NO_PROXY` 没有排除测试域名，再用 FlClash 连接记录核对实际路径。PowerShell 示例：

```powershell
$proxyPort = 7890
$testUrl = 'https://example.com/'
curl.exe -q --proxy "http://127.0.0.1:$proxyPort" --connect-timeout 5 --max-time 15 -sS -o NUL -w 'http=%{http_code}\n' $testUrl
```

仅在用户确实需要 UDP 时，用经过同一代理链的实际 UDP 请求及有效响应验收。SSH 动态转发只作为已授权的临时 TCP 对照，绑定环回地址并核对主机指纹。长期出口使用用户选定的持久服务，切换完成后关闭临时隧道再复测。

## 定位握手与回程

先从控制台或已可用的 SSH 核对 VPS 的监听端口、监听地址族、系统防火墙、云防火墙及回程路由。Linux 上可用 `sudo ss -lntp`，需要 UDP 时另用 `sudo ss -lnup`。用已识别的服务单元名检查 `systemctl status <unit>` 和 `journalctl -u <unit> --since ...`，按复现时间读取日志。

需要确认握手断点时，在两端同时采集短时、按目标和端口过滤的包头。Windows 可用管理员权限运行 Pktmon，并核对物理网卡；Linux VPS 可用如下命令，替换示例端口和客户端公网地址：

```bash
sudo timeout 20s tcpdump -nn -i any -s 96 -c 40 'tcp port 18444 and host 192.0.2.20'
```

核对时间、端口和报文序号；有 NAT 时匹配转换后的连接。只保留必要的握手摘要。根据同一次连接的证据解释：

| 观测 | 下一步 |
| --- | --- |
| 客户端发出 SYN，VPS 未见对应 SYN | 核对目的地址、抓包位置和过滤条件，然后检查入站路由及上游过滤。 |
| VPS 收到 SYN，未见发出 SYN-ACK | 核对服务监听、主机防火墙、回程路由以及是否有 RST。 |
| VPS 发出 SYN-ACK，客户端物理接口未见对应回包 | 检查回程路径并补独立网络对照。现有证据只支持该回包未在客户端捕获。 |
| 双端确认 TCP 握手完成 | 继续查 SSH banner、认证或代理协议与实际转发。 |

提交工单时附时区与复现时间、源网和目标 IP/端口、监听状态、双端握手摘要、独立网络对照，以及请网络方核查的方向。IPv4 某个端口的超时结论只覆盖已测地址、端口和网络。

## 修复服务并验证

- **监听或服务失败**：先查当前生效的 unit、进程用户和日志。若 systemd 服务因权限无法读取受限配置，确认系统版本和现有 `ExecStart` 参数后，可用 `LoadCredential=` 给服务交付配置，并让进程读取 `${CREDENTIALS_DIRECTORY}` 中的对应文件。备份 unit 或 drop-in，保留原文件权限和所需启动参数。执行授权的服务重载或重启后，从服务状态、实际监听、外部转发三个层面验收。脚本输出和开机自启设置分别只证明对应阶段。
- **部分路径可用**：经用户选定的可用地址族或备用节点恢复业务，分别验证管理登录、代理入口、VPS 出站和原应用。原路径的故障保留为待查项。已验证的服务重启和整机重启恢复分别记录；只有需要验收开机恢复且有维护窗口时，才安排整机重启测试。
- **选组或分流失败**：备份活动 profile，校验实际加载的节点与规则引用，修改最小范围，重新应用后用目标请求确认完整链路。逐组记录预期链路与 HTTP/业务结果。配置和日志只输出脱敏摘要，密码在本地或服务端受限存储中更新。

会话中的对照案例是 IPv4 入口部分端口握手异常，VPS 已发出回包但客户端未捕获；经 IPv6 接入代理后，HTTPS 请求走 VPS 的公网 IPv4 出口。后续在维护窗口实测了代理服务随整机重启恢复，也逐组验证了客户端转发。将这些结果按入口、出口、开机恢复和业务验收分别记录。
